# Implementation Plans

Generated by the `improve` skill on 2026-07-21 from a React-focused performance
audit of the composite Perses workspace. The plans live at this workspace root
because they span the sibling `shared`, `perses`, and `plugins` repositories.
They were planned against shared commit `f8cd4b7`, perses commit `06886ac1`, and
plugins commit `d7075da`.

Plans 017–025 were added later the same day by a second `improve` run focused
on **state handling** (dashboard, variable, query state). Same commits; same
toolchain rules. They complement — and must not duplicate — plans 001–016.

Plans 026–034 are the former `fable-plans/` set (a 2026-07-20 audit focused on
**React re-renders and computation**, same commits), merged into this index on
2026-07-21 and renumbered 001–009 → 026–034. Their plan bodies keep their
original per-repo scoping ("Repo `shared`" etc.) and their branch names now
match the new numbering. See "Overlap between audit sets" below before
executing any of them.

Plans 035–047 come from a third `improve` run on 2026-07-21 (same commits)
focused on **bugs — technical and non-technical (copy/UX/a11y) — in React
code**, covering areas the first two audits skipped: `shared/explore`,
`shared/components` form/dialog widgets, app views outside dashboards, auth
flows, and panel plugins beyond the hot render paths.

Execute in the order below unless dependencies say otherwise. Independent plans
in the same wave may run in parallel. Each executor must read its plan fully,
honor its STOP conditions, run commands from the composite workspace root unless
the plan says otherwise, and update its row when done. On Windows PowerShell,
use `npm.cmd` where the `npm.ps1` execution policy blocks `npm`; on Unix-like
shells, use `npm`.

All three JavaScript workspaces pin Node `v22.14.0` in `.nvmrc` and npm
`10.9.2` through `packageManager`. Activate those versions before install or
verification commands. The audit host's Node 24/npm 11 combination was not a
valid substitute: the Perses app Jest configuration failed before loading a
test under that toolchain.

## Findings considered and rejected

- **Blanket `memo`, `useMemo`, `useCallback`, or hoisted `sx` changes:** rejected
  because they add comparison and maintenance cost without evidence that a
  memoized child or expensive computation benefits. The plans target measured
  subscription and hot-loop boundaries instead.
- **Treating repeated `usePlugin` calls as duplicate network requests:**
  rejected because React Query already deduplicates identical query keys. Plan
  014 targets serial exposure imports and coarse module caching, which remain
  real costs after request deduplication.
- **Adding virtualization to every table path:** rejected because current table
  paths already use Virtuoso or DataGrid where appropriate. Plans 005 and 013
  address avoidable work inside those existing render/preprocessing paths.
- **Replacing every dashboard selector that returns an object:** rejected
  because `useDashboardStore` already applies shallow comparison. Plans 007 and
  008 cover the actual fresh-object, whole-map, and whole-resource subscription
  boundaries.
- **Adding route-level code splitting as a new initiative:** rejected because
  the application router already lazy-loads route modules. Plans 014 and 015
  instead isolate heavyweight plugin-runtime and component entry points that
  still leak into initial chunks.

From the 2026-07-21 state-handling audit:

- **`useTimeRangeParams` returning the `initialTimeRange` argument as the live
  `timeRange`** (`shared/plugin-system/src/runtime/TimeRangeProvider/query-params.ts:125-154`):
  rejected as by-design — every caller derives that argument from
  `useInitialTimeRange`, which is itself URL-param-reactive, so the value does
  follow the URL. Only the naming is misleading; not worth churn.
- **`DataQueriesProvider` context identity, variable context value stability,
  and the `JSON.stringify` selector equality**: already planned in
  plans 026, 027, and 032 (formerly `fable-plans/001`, `002`, `007`).
- **`usePanelEditor` seeding local state from `panelDefinition` once**
  (`shared/dashboards/src/components/PanelDrawer/usePanelEditor.tsx:31-44`):
  the drawer remounts per editing session in practice; MED confidence only —
  investigate if a stale-draft bug is ever reported, no plan now.
- **`PanelEditorForm.handlePanelDefinitionChange` rollback guard using `&&`**
  (`shared/dashboards/src/components/PanelDrawer/PanelEditorForm.tsx:118-123`):
  matches the code comment's stated intent; LOW confidence that it is wrong.
  No plan.

From the 2026-07-20 re-render audit (merged from `fable-plans/`):

- **Inline `sx` props on MUI components generally:** idiomatic MUI, not worth
  churn outside hot 100+-item loops.
- **`Row.tsx:56` `WidthProvider(Responsive)` in `useMemo`:** per-instance
  component creation is intentional (per-row width provider); memoized
  correctly with `[]`.
- **`DataQueriesProvider` component internals (`queryDefinitions` rebuilt per
  render):** downstream `ctx` useMemo deps already dominated by react-query
  result identity churn; low leverage until react-query v5 migration.
- **`EChart` deep `isEqual(prevOption, option)` on every option change
  (EChart.tsx:204):** expensive but load-bearing (prevents setOption churn);
  revisit only with profiling after plans 026/029 land.
- **App-shell code splitting at route level:** out of the re-render focus;
  covered separately by plans 014/015.
